# Draft response to CE Merging Server integration feedback

**To:** Marc-André Lemburg

**Subject:** Response to *CE Merging Server v1.2.0 – Integration Feedback*, version 2 (2026-11-12)

> Draft for developer and product-owner review before sending. The actions below are proposed responses to the findings, not a statement that fixes have already been implemented or scheduled.

Thank you for the detailed report and for providing reproducible observations from both source review and live integration runs. The distinction between blockers, major issues, minor issues, and questions is useful, and we understand that the removed IGM details do not change the findings. We have compared the report with the current source/configuration snapshot; this response does not claim that any reported issue is already fixed.

Our proposed order is to address the two merge blockers and data-integrity risks first, then improve task recovery and API diagnostics, and then resolve deployment, logging, output-contract, and documentation issues. We will not infer missing operational or format requirements where the report asks for a product decision.

## Proposed responses by finding

### Blockers and input correctness

- **CE-01 — BCI with no EC or feasibility range (blocker):** We agree that an unbounded interval represented by extreme finite values is unsafe for arithmetic and that the resulting error is not actionable. Until a business-approved finite source of limits is identified, the safer behavior is to reject the run during validation with the affected area and missing constraint named, rather than silently treating it as unconstrained. Please confirm whether IT and CH are expected to have BCI hubs and, if so, which approved data source supplies their limits.
- **CE-02 — PEVF namespace/document type (blocker):** We agree that an unsupported document must not be reported as though its time interval were absent. We propose validating the root namespace/document profile and returning an explicit supported-format error. The accepted profile should be documented with its version, EIC level, reference area, required exchanges, and ALEGrO requirements. Please confirm whether F237 2:1 is the required format or whether Vulcanus 2:0 support is also needed; a known-good reference sample would help lock down the contract.
- **CE-03 — PEVF content validation and implicit zero flows (major):** We agree that required content should be checked before the expensive merge steps and that missing exchanges must not disappear into a warning. Our proposed default is to fail early with a consolidated list of missing required exchanges, including the relevant file and step. A missing flow should be an error unless zero is explicitly agreed as its semantic; if zero is valid, it should be visible in a structured result, not only in a log.
- **CE-13 — Required but unused inputs (question):** We will clarify for each input whether it affects computation, is only retained/copied, or is reserved for future use. Inputs that do not affect the current result should not be presented as if they do. Please confirm whether IGM QC verdicts are intended to filter IGMs, whether `basecase-improvement-parameters` is intended to control BCI (including `runBCI`), and whether `dc-load-flow-parameters` is expected to be used. Once agreed, the API metadata and required/optional status should match that behavior.
- **CE-14 — IGM filename date/time/version (question):** We understand that previous-day FO replacements may be valid and should not necessarily be rejected. We propose retaining the current acceptance behavior unless the product contract says otherwise, while reporting a filename timestamp that differs from the task target date in a warning or task output. Please confirm the intended mismatch policy and whether the daily report counts IGMs by type code only.
- **CE-15 — Missing required areas found late (minor):** We agree that required-area checks should happen before substantial computation. We propose a start-of-run preflight that checks the areas required by the selected processing steps and reports all missing areas together. This avoids rejecting inputs for areas that are not required by a particular configuration while preventing late failures such as the reported ES case.

### API errors and task lifecycle

- **CE-04 and CE-09 — Failure detail and failed-step attribution (major):** We agree that a client must be able to recover the failure reason after a synchronous request is interrupted. We propose exposing a stable error code, human-readable detail, failed step where known, and a message-only cause chain both in the error response and in the task representation. The error contract should not require clients to parse message prefixes.
- **CE-05 — Empty 400 responses (major):** We agree that rejected requests need actionable error documents. We propose returning the existing JSON:API error shape consistently for validation, already-running, and not-yet-finished cases, including missing or misnamed input files where applicable. A rejected create should also avoid consuming an externally visible task ID if feasible.
- **CE-06 — Intermittent execution-log download failure (major):** The reported cause is not confirmed, so we will treat this as an investigation rather than assume the suspected H2 race is proven. We propose logging unhandled endpoint exceptions with a correlation/task identifier, making log publication/readiness explicit when a run reaches `SUCCESS`, and testing immediate downloads under load. A temporary client retry may remain a useful workaround but should not be the only reliability measure.
- **CE-07 — Tasks left `RUNNING` after restart (major):** We agree that an interrupted task must not remain permanently indistinguishable from an active run. We propose marking tasks that were `RUNNING` at startup as `ERROR` with an interruption detail. Automatically resuming a merge is not proposed because its safety/idempotency has not been established. Please advise whether a run timeout or cancel/abort endpoint is required in addition.
- **CE-11 — Daily API repeated run and core task validation (major):** We agree that a second request must not change the status of the first active run. The daily API should handle `TaskAlreadyRunningException` separately from processing failures, validate that referenced core tasks exist and are finished, and reject duplicate target dates with a structured 400 listing the problems. We also propose aligning its response shape with the core API, or documenting why it differs.
- **CE-12 — Missing/unproduced output behavior (minor):** We propose one consistent response for an output that was not produced, such as a JSON:API 404, while reserving 500 for an actual server failure. This should apply across all artifact and output endpoints, including task-error cases.

### Persistence, security, and operations

- **CE-08 — H2 initialization drops log tables (major):** We agree that schema initialization must not delete execution history on each new connection. We propose replacing the destructive initialization with a one-time/idempotent schema migration and defining explicit log retention or task-linked deletion. The persistence behavior should be covered by a restart and connection-recycle test.
- **CE-10 — Authentication, H2 console, and container user (major):** We agree that the current defaults are not appropriate for an exposed or shared deployment. We propose disabling the H2 console by default, running the container as a non-root user, and documenting the intended network boundary and security assumptions. Authentication should be required for shared/untrusted access; the specific mechanism (for example, an OAuth2 resource server or a deployment-provided gateway) needs a deployment decision. Until then, the service should be described as internal-only rather than implicitly safe for public access.
- **CE-27 — Task/file/log retention (minor):** We propose configurable retention by age and/or count, with task inputs, outputs, artifacts, and execution logs removed consistently. Defaults and any audit-retention requirements need to be agreed before enabling automatic deletion.
- **CE-28 — Synchronous API and capacity (question):** We cannot infer safe parallel capacity from the reported single-run timings. We propose measuring concurrent runs—including the expected burst of up to 24 timestamps—before publishing a capacity limit, and checking shared state such as H2, configuration caches, and compute resources. An asynchronous `202 Accepted` workflow with polling is worth evaluating, especially to avoid long-held HTTP connections and loss of synchronous error details; please confirm whether this is a required integration direction.

### Logging, configuration, and output contract

- **CE-16 — MDC/task/step attribution (minor):** We agree that request and step context must not leak across reused threads. We propose scoped MDC cleanup, setting the TSO context before logging the import, assigning explicit tags to pre-treatment and calculation steps, and propagating context to executor work where supported.
- **CE-17 — Log timestamp consistency (minor):** We propose using an unambiguous ISO 8601 timestamp with an offset for execution records. OLF report entries should carry their actual event time if available; otherwise, they should not be assigned a misleading conversion-time timestamp.
- **CE-18 — Failures missing from logs (minor):** We agree that failures should be logged once at the task boundary or at the relevant step, with the step and task context and without duplicating stack traces. This includes PiSa and slack-compensation failures.
- **CE-19 — Logging configuration and served exceptions (minor):** We propose keeping useful web/container exception logging enabled, reducing high-volume OLF database logging where appropriate, and including the exception message (not a stack trace) in served execution logs. An asynchronous database appender can be evaluated, but correctness and durability should be verified before changing appender behavior.
- **CE-20 — Default-configuration fallback messages (minor):** We agree that “retrieved” should only be logged when a configuration was actually found. A missing published record should produce a single clear fallback message without a misleading `NullPointerException` stack trace.
- **CE-21 — Region configuration source/shape (minor):** We propose removing or wiring the stale YAML region block so there is one authoritative default, and using a consistent documented JSON shape for the region configuration endpoint and bundled configuration.
- **CE-22 — Default X-node configuration (question):** Please confirm whether the built-in X-node configuration is intended for production or is only a fallback that deployments must replace. We also need a decision on whether missing HVDC-link X-nodes should be configured explicitly or treated as out-of-BCI. Once agreed, the defaults and warnings can be aligned with that policy.
- **CE-23 — Merging-report labels/names (question):** The report identifies a real mismatch between `CE`/`nonCE`/`TSO` labels and `CORE`/`nonCORE` platform examples and fixtures. Please identify the authoritative CE output contract and the owner of the schema decision. We propose updating implementation, fixtures, and documentation together, and considering a clearer “merging report” artifact name if compatibility permits.
- **CE-24 — Numeric precision and `MergeType` (minor):** We agree that inconsistent rounding and `xs:short` overflow/wraparound are risks. We propose one documented rounding rule, range-safe numeric types (or explicit range validation), and tests around boundaries. The meaning of `MergeType` should be documented; if it is intended to represent both balance-adjustment and final-loadflow fallback, both states should be reported rather than inferred from one.
- **CE-25 — CGM filename and publication point (minor):** We propose using the UCTE repeated-hour marker for the second occurrence of the autumn DST hour and validating filename date/time/version against the agreed naming rules. Please confirm whether the downloadable CGM is intended to be the state before or after final loadflow. We propose making CGM availability consistent with task status so a task ending in `ERROR` does not expose a file that appears to be a completed result unless that behavior is explicitly intended.
- **CE-26 — CGM quality report and validation (question):** The report notes similar paired-tie-line findings on the platform sample, so we agree these findings should not be attributed to this merger without a confirmed validation rule. Please confirm whether QAR/COR output is in scope, which X-node representation is intended, which loadflow parameters define validation, and whether flat-start convergence of the exported CGM is a requirement.

### Example input package

- **CE-29 — Example ZIP inconsistencies (minor):** We agree that the example must be a reliable integration contract. We propose regenerating it from a validated run and checking that the request JSON parses, the target date and file timestamps align, required input files are present, region membership is consistent, the F301 tie-line count matches its entries, and the MergedFR date convention and F301 time coverage are documented. The intended handling of an IE IGM outside the CE region should also be stated explicitly.

## Decisions requested

To finalize implementation and documentation, we request confirmation on:

1. The source and policy for IT/CH BCI limits, including whether missing limits should reject a run.
2. Supported PEVF namespaces/profiles and a reference sample; whether missing flows are errors.
3. Whether IGM QC verdicts affect inclusion and whether the three reported unused input types are intended to affect computation.
4. Whether filename timestamp mismatches should warn or fail, and the daily report’s IGM counting rule.
5. Authentication/deployment model, expected peak concurrency, and priority of an asynchronous API.
6. Production ownership of default X-node configuration and the expected handling of HVDC X-nodes.
7. The canonical merging-report labels/schema and the intended CGM state, naming convention, and quality-validation contract.
8. Retention requirements and whether cancellation/timeouts are required.

Once these contract decisions are agreed, we can turn the proposed responses into a prioritized implementation and verification plan. No delivery dates are included here because scope and priority have not yet been confirmed.
